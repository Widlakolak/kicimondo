# Stage 07: Java content backend

Status: implemented for owner review. PR #6 is merged and its CI passed (60 unit and 19 browser tests, Android APK). The owner approved continuing before manual Stage 05/06 and physical Stage 04/05/06 Android reviews. Native upgrade durability remains pending.

## Goal

Publish immutable, validated educational content packs through a small Java REST service. Demonstrate that a running web or Android client can explicitly obtain compatible new math variants, persist a validated pack locally, and use it offline after restart. The bundled Stage 06 game remains fully playable without any backend.

## Scope and contract

- Create backend/ with Java 21, a compatible stable Spring Boot 4.x, Gradle Kotlin DSL and a checked-in wrapper, Spring Web MVC, Validation, Data JPA, PostgreSQL, Flyway, Actuator, compatible OpenAPI and JUnit Jupiter/Testcontainers. Verify current dependency/toolchain compatibility from official sources; pin exact versions. No floating tags or new unrelated frontend upgrades. Feature-oriented modular monolith, clear DTO/domain/persistence boundaries, no unnecessary abstractions.
- Define a small shared JSON contract under contracts/ for educational variant packs, plus valid/invalid fixtures. Keep existing frontend TypeScript definitions authoritative for maps, quests, rewards, effects, localization, cat and habitat rules. Export a generated capability/quest manifest from the current content definitions (not a hand-maintained duplicate) and consume it in Java validation; CI checks that it remains current. No runtime executable code, remote assets or arbitrary links.
- First remote pack scope: variants of existing MATH_CHOICE challenges only. A pack contains a stable pack ID, immutable positive version, schema version, compatible bundled content version (currently 4), locale pl, and bounded variants keyed by existing challenge ID, with stable variant ID and seed. Optionally permit approved operation sequences and maximum <=10 only if matching the existing learning objective and supported rendering. Keep skill, instructions, picture/counter IDs and reward/effect definitions bundled. Use the same deterministic math algorithm in Java and TypeScript or share generated question vectors; validate exact one correct answer, distinct choices, nonnegative subtraction and result <=10. Do not alter quest IDs, PS, maps or save/content schema semantics. No runtime arbitrary text or downloaded scripts. Bound total bytes/counts/strings and validate unknown fields, duplicates, cross references and incompatible versions in both runtimes.
- Separate educational pack version from the existing save schema 3/content 4. Do not bump save schema merely for a downloaded math pack. Preserve all 25 quests and existing records. Pin the selected variant and seed for a challenge attempt; switching packs never awards a point or resets progress.
- Use PostgreSQL and Flyway for pack metadata and validated payload (e.g. JSONB). Immutable published versions, unique ID/version, transactional publication with conflict handling and a latest-compatible query. A repeated identical publication is idempotent; different content for the same ID/version is rejected. Use JPA entities and migrations with ddl-auto=validate. No H2 substitution. Seed a real demo pack through a repeatable documented local import path; no runtime uncontrolled automatic imports.
- Public read-only API under /api/v1/content/packs for listing compatible packs/latest metadata and fetching an exact immutable version. Provide consistent ProblemDetail errors, validation, 404/409 where appropriate and an integrity checksum over explicitly defined canonical bytes (or raw exact serialized payload). ETag/If-None-Match optional if justified. OpenAPI documented examples. Choose and document exact paths. Actuator health only, no sensitive management endpoints. No public write endpoint: use a small operator-only CLI/import task reading a local file and calling the publication service, or an equivalently safe offline operator workflow. Do not add admin authentication/accounts in this stage. No credentials in Git.
- Demonstrate client integration via an optional Polish menu action, intended for adult use, to check/download a compatible educational pack. Default is bundled content and no configured remote service; use explicit development/build configuration, same-origin /api for web when deployed later, explicit HTTPS endpoint for native when configured. For local native test document safe development-only connection; never globally relax cleartext/TLS security. No automatic network calls or telemetry, no child profile data sent. No arbitrary server URL input exposed to children. Bounded timeout and size, strict validation of untrusted JSON, checksum verification where supported with a compatible strategy, reject unsupported or invalid packs; preserve the last valid cache. Save the validated pack and activation selection separately from gameplay in IndexedDB. Activate only at the menu or another safe boundary, never during a challenge. Cache may be used offline after reload/restart; if missing/invalid/incompatible, fall back to bundled content without altering progress. Allow returning to bundled content. No gameplay dependency on API or backend availability.
- Add Dockerfile for backend and separate local Compose configuration for backend + pinned PostgreSQL with private DB networking and persistent named volume, health checks, configurable environment and .env.example with non-secret development placeholders. Bind development API to localhost by default; document test configuration. No GHCR publication, QNAP, domain or tunnel changes yet. Java container must be appropriate for modest x86-64 NAS later; do not claim measured QNAP performance. Avoid Kafka, Redis, microservices and paid services.
- Add backend GitHub Actions checks (JDK 21, Gradle wrapper, unit/integration tests against real PostgreSQL via Testcontainers, bootJar, contract validation). Preserve frontend CI, Android build and APK artifact; increment distributed Android versionCode to 7/versionName 0.7.0 if frontend changes ship. Keep Android API 24, Chromium 80, Node/npm pins, stable app ID/origin, native lifecycle and offline PWA updates. No signing keys or store publication.

## Acceptance

- From a clean PostgreSQL instance, Flyway creates schema and an operator imports a valid sample pack. Read it through REST; a second version is published immutably. Incompatible clients receive no incompatible pack. Duplicate identical import is safe; conflicting version, malformed/oversized payload, unknown challenge, unsupported schema, invalid math parameters and invalid references fail without partial publication. Verify persistence across service restart, HTTP 404 for incompatible reads, CLI rejection of conflicting versions and OpenAPI.
- Run Java unit tests and actual PostgreSQL integration tests, including migrations, constraints, transactional publication, compatibility lookup, endpoint responses and shared math/contract fixtures. Run local Compose configuration validation and smoke if Docker is available. Clearly state any tool limitation rather than claiming success.
- Web client with configured local test API downloads a valid math pack explicitly, starts an existing quest with a demonstrably different valid math variant, completes it offline and retains only the original 1 PS reward. Reload offline and use cached pack in another eligible quest. Test failed fetch, timeout, invalid/unsupported/oversized pack, safe fallback, switching back to bundled, no network in default mode, and preservation of the Stage 06 save with 25 PS, discovered cats and trust. Test activation only at a safe boundary and no remote scripts. Use real backend for at least one integration smoke where available; mocked browser tests are separate.
- Verify all existing gameplay/CI, PWA precache and update tests, Android packaging and legacy Chromium target. No claim of actual MediaPad T5 performance, native network or upgrade success until tested. Document exact Windows PowerShell startup, operator import, curl/Invoke-RestMethod API usage, client configuration, tests and shutdown (no volume deletion).
- Update README, roadmap, architecture, content, deployment and stage notes. Record actual tests and pending owner reviews. Keep repository docs/code concise English and UI Polish.

## Verification

- Node.js 24.13.1 and npm 11.11.0 passed strict installation, lint, type checks, contract manifest validation, 80 unit tests and the production build. All 22 Playwright tests passed, including the existing offline and Android layout regressions.
- The new browser tests use mocked HTTP responses. They cover explicit activation, bad downloads, offline reload and use in two existing quests, returning to bundled content, preservation of a 25 PS save, and the original single reward for the water quest.
- On Java 21, the Gradle Wrapper checksum matched the published Gradle checksum. All four Java unit tests and five PostgreSQL Testcontainers integration tests passed. The executable JAR built successfully.
- Local Compose validated and started with healthy PostgreSQL and backend containers. A real import published the demo pack. Reimport preserved its checksum and a conflicting payload failed. After backend recreation the API still served the original bytes. Compatibility filtering, checksum, OpenAPI, Swagger UI and minimal health were checked over HTTP.
- On Linux, Chromium 80.0.3987.0 and Chromium 156 downloaded the demo pack from the live Compose API, reloaded offline and completed the existing water quest for 1 PS.
- The universal Android debug APK built and passed signature, application ID, API 24 minimum, target API 36 and version 0.7.0 (7) checks. It bundles the game and retains the native `https://localhost` origin. Physical MediaPad T5 compatibility, performance, HTTPS API connectivity and same-key upgrades remain pending.
